# 真实路由记忆提取的代码复用、Campaign 隔离与数据库存储设计

- 文档版本：v1
- 创建日期：2026-08-06
- 当前状态：设计方案，尚未实现
- 关联文档：[真实路由记忆提取与成本Token统计方案.md](真实路由记忆提取与成本Token统计方案.md)

## 1. 背景与目标

当前训练流程会为每个主题段预生成完整的 small、medium、large 三层候选记忆。强化学习训练期间，路由动作从冻结的 L/M/H 候选集合中选择事实并组装数据库 S，不会在每个 rollout 中重新调用记忆提取模型。

最终 outer-test 评估需要增加一条更接近真实部署的流程：

```text
冻结路由器
→ 逐 segment 选择唯一 tier
→ segment 只进入被选中的 buffer
→ 调用对应 tier 的记忆提取模型
→ 记录真实 API 调用、Token 和费用
→ 写入本次部署专用记忆库
→ 组装 S
→ 执行 QA、Reader 和 Judge
```

本设计需要同时满足：

1. 训练候选提取与真实路由提取共用同一套底层提取协议。
2. 不改变训练候选阶段“每个 segment 进入全部三个 tier”的行为。
3. 不破坏 extraction campaign 的不可变范围和完整性检查。
4. 不让真实测试数据污染训练候选账本和 Qdrant collection。
5. 保持现有 `qdrant_fact_v2` 数据结构与 QA 检索路径。
6. 真实调用、Token、费用、repair、retry 和失败均可审计。

## 2. 总体结论

推荐采用以下原则：

> 共用提取内核，分离候选生成编排与真实路由编排；共用 Fact/Qdrant schema，分离 namespace、manifest 和 SQLite 账本。

具体来说：

- 底层 buffer、API、解析、repair、Token、费用、FactRecord 和 Qdrant 写入逻辑应当公用。
- 当前 `CandidateGenerator.generate()` 不能直接用于真实路由提取。
- 应新增 `RoutedMemoryExtractor` 或等价的独立编排器。
- 训练 campaign 继续只管理完整 L/M/H 候选生成。
- routed-test 使用独立的 deployment manifest、run lock、输出目录和 Qdrant namespace。

## 3. 当前训练候选提取语义

当前 `CandidateGenerator.generate()` 的核心行为是：

```python
for segment in segments:
    for tier in selected_tiers:
        buffers[tier].add(segment)
```

因此：

```python
generate(segments, tiers=("small", "large"))
```

表示：

```text
所有 segment → small
所有 segment → large
```

而不是：

```text
一部分 segment → small
另一部分 segment → large
```

这种语义适合训练候选生成，因为训练需要每个 segment 的 L/M/H 三种反事实记忆，以便不同路由动作共享冻结候选。

## 4. 真实路由提取需要的语义

真实路由阶段应输入唯一动作映射：

```python
route = {
    "segment-A": "small",
    "segment-B": "large",
    "segment-C": "medium",
}
```

实际入 buffer 逻辑应为：

```python
for segment in segments:
    tier = route[segment.segment_id]
    buffers[tier].add(segment)
```

必须满足：

- 每个输入 segment 在 route 中恰好出现一次；
- 每个 route action 必须属于 small、medium、large；
- 每个 segment 只进入一个 tier buffer；
- buffer 不跨 sample；
- sample 结束时三个 buffer 分别 finalize；
- 没有 segment 的 tier 不产生 batch 和 API 调用。

## 5. 可公用的底层组件

以下能力应由训练候选和 routed-test 公用：

| 能力 | 当前组件 | 公用要求 |
|---|---|---|
| 提示词渲染 | `render_extraction_prompt` | 使用相同 prompt 和 topic marker |
| JSON batch 渲染 | `render_batch` | 保持 segment 顺序 |
| 分 tier buffer | `ExtractionBuffer` | 使用完全相同的 overflow/flush 规则 |
| Buffer 构建 | `build_tier_buffers` | 支持只创建实际使用的 tier |
| 超长段处理 | `prepare_extraction_segments` | routed 模式按该 segment 的实际 tier 检查 |
| API 客户端 | `OpenAICompatibleClient` | 统一 timeout、retry 和 provider usage |
| JSON 解析 | `parse_fact_batch` | 统一 schema 和 segment/source 校验 |
| Schema repair | `render_json_repair_prompt` | 统一 repair 上限与账本 |
| Source 归属 | `_allowed_source_ids` | 每个 fact 严格限制在一个 segment 内 |
| Token/费用 | `ProviderUsage`、`allocate_batch` | 使用相同价格公式和分摊规则 |
| Fact 数据 | `FactRecord` | 继续使用 `qdrant_fact_v2` |
| Fact embedding | memory encoder | 模型和向量维度一致 |
| Qdrant 写入 | `replace_candidate_batch` 的底层能力 | 按 run/batch 幂等写入 |
| S 组装 | `AssemblyManager` | 只复制本次 run 的选中 tier facts |
| QA 评估 | `AssemblyEvaluator` | 继续只读取指定 S assembly |

## 6. 推荐的代码分层

推荐重构为三层：

```text
ExtractionEngine
├── prepare segment
├── build buffer
├── flush batch
├── call API
├── record attempts
├── schema repair
├── validate sources
├── allocate tokens/cost
├── build FactRecord
├── embed facts
└── write Qdrant/SQLite

CandidateGenerator
└── 每个 segment → small + medium + large

RoutedMemoryExtractor
└── 每个 segment → route[segment_id] 指定的唯一 tier
```

建议文件结构：

```text
infobudget/rl_router/extraction_engine.py
infobudget/rl_router/candidates.py
infobudget/rl_router/routed_extraction.py
scripts/evaluate_routed_deployment.py
```

### 6.1 ExtractionEngine

负责所有提取阶段共用逻辑，不决定一个 segment 应进入哪些 tier。

建议接口：

```python
class ExtractionEngine:
    def run_assignments(
        self,
        *,
        segments: list[TopicSegment],
        assignments: dict[str, Tier],
        extraction_run_id: str,
        run_scope: dict,
        resume: bool = False,
    ) -> ExtractionSummary:
        ...
```

其中 `assignments` 必须对每个 segment 给出唯一 tier。

### 6.2 CandidateGenerator

保留原有对外语义，内部构造三个 assignment 流或调用通用 engine：

```text
small assignment：全部 segment → small
medium assignment：全部 segment → medium
large assignment：全部 segment → large
```

训练脚本、campaign、replay history 和 reconciliation 的行为保持不变。

### 6.3 RoutedMemoryExtractor

接收冻结路由器产生的真实 route：

```text
每个 segment → 唯一 tier
```

只形成实际使用 tier 的 batch，不要求每个 sample 的 L/M/H 全部完成。

## 7. 不建议直接修改的行为

为降低训练回归风险，不建议：

1. 改变 `CandidateGenerator.generate()` 的默认 tier 语义。
2. 让同一个参数同时表示“所有段进入这些 tier”和“每段选择一个 tier”。
3. 将 routed-test extraction run 写入训练 `candidate_ledger.sqlite3`。
4. 将 routed-test run 加入 campaign `expected_runs`。
5. 修改 campaign 的 `required_tiers` 来适配 routed-test。
6. 让训练脚本自动发现 routed-test 的 segment cost。
7. 仅依赖 `freeze_candidates()` 作为服务器级数据库写锁。

## 8. 初次 Fact 的主题段边界

无论训练候选还是 routed-test，每个初次提取 fact 均必须：

- 只有一个 `segment_id`；
- 全部 `source_ids` 属于该 `segment_id`；
- 不允许一个 fact 同时使用主题段 A 和 B 的 source；
- 不允许为了跨段总结而把 A/B 合并成一个新的提取 batch 语义单元；
- 跨段推理由 QA Reader 检索多个独立 fact 后完成。

假设：

```text
segment-A sources = {0, 1}
segment-B sources = {2, 3}
```

允许：

```json
{
  "segment_id": "segment-A",
  "source_ids": [0, 1],
  "fact": "A standalone fact."
}
```

禁止：

```json
{
  "segment_id": "segment-A",
  "source_ids": [0, 2],
  "fact": "A cross-segment fact."
}
```

结构校验可以判断 source ID 是否属于 segment，但不能完全判断 source 文本是否在语义上直接支持 fact。因此正式实验还应记录 provenance 抽样审计结果。

## 9. Campaign 隔离设计

### 9.1 当前训练 Campaign 的职责

训练 extraction campaign 锁定：

- dataset、split 和 segmentation method；
- 每个 sample 的 segment 文件哈希；
- 每个 sample 的预期 extraction run ID；
- `required_tiers = small + medium + large`；
- 模型和提示词；
- extraction config；
- embedding hash；
- collection namespace template。

campaign 只有在所有预期 sample 的三个 tier 均完整完成后才能成为 complete。

### 9.2 Routed-test 不属于训练 Campaign

routed-test 每个 segment 只提取一个 tier，不满足训练 campaign 的完整 L/M/H 定义。因此应创建独立 manifest：

```json
{
  "schema_version": "deployment_evaluation_v1",
  "run_type": "routed_test_extraction",
  "source_campaign_id": "campaign-id",
  "source_campaign_scope_hash": "sha256",
  "fold": 0,
  "partition": "test",
  "checkpoint_sha256": "sha256",
  "route_hash": "sha256",
  "split_manifest_sha256": "sha256"
}
```

routed-test 可以引用训练 campaign 的 ID 和 hash，但不得更新训练 campaign manifest。

## 10. 三类锁的区别

### 10.1 Campaign Scope 锁

`campaign_scope_hash` 用于阻止同名 campaign 被不同数据、模型、prompt 或 extraction config 覆盖。

它是实验范围锁，不是 Qdrant 数据库写锁。

### 10.2 Extraction Run 锁

每个 extraction run 使用：

```text
run.lock
state.sqlite3
```

`RunFileLock` 防止两个进程同时运行同一个 run；`ExtractionRunState.scope_hash` 防止用不同范围错误 resume。

routed-test 应复用该锁，但 routed scope hash 必须额外包含：

- fold；
- partition；
- split manifest hash；
- checkpoint hash；
- scaler hash；
- `segment_id → tier` route；
- route hash；
- segment 内容 hash；
- prompt/model/config hash；
- Qdrant namespace。

当前候选 `_scope_hash()` 不包含 route action，不能原样作为 routed-test 的完整 scope hash。

### 10.3 `freeze_candidates()`

当前 `freeze_candidates()` 只设置当前 `FactQdrantStore` 实例的内存布尔值。

它可以防止训练进程中的该 store 实例继续写 L/M/H，但不是 Qdrant 服务器级全局锁。另一个 writable store 实例仍可能写入相同 collection。

因此 routed-test 必须依靠 namespace 和 run ID 隔离，不能只依赖 `freeze_candidates()`。

## 11. Qdrant 存储设计

### 11.1 当前 Collection 结构

每个 namespace 创建四个 collection：

```text
<namespace>_L
<namespace>_M
<namespace>_H
<namespace>_S
```

映射关系为：

| Tier | Collection 后缀 |
|---|---|
| small | L |
| medium | M |
| large | H |
| assembled | S |

### 11.2 推荐独立 Deployment Namespace

训练候选继续使用当前 namespace，例如：

```text
longmemeval_full_segversion_embeddinghash_L
longmemeval_full_segversion_embeddinghash_M
longmemeval_full_segversion_embeddinghash_H
longmemeval_full_segversion_embeddinghash_S
```

routed-test 使用独立 namespace，例如：

```text
longmemeval_cv5_fold0_deploy_runhash_L
longmemeval_cv5_fold0_deploy_runhash_M
longmemeval_cv5_fold0_deploy_runhash_H
longmemeval_cv5_fold0_deploy_runhash_S
```

优点：

- 不修改训练 collection；
- 不需要迁移 vector schema；
- 不会被遗漏 `extraction_run_id` 的查询误读；
- 可以独立清理一次 deployment evaluation；
- campaign reconciliation 不会扫描到 routed-test points；
- `freeze_candidates()` 不是全局锁的问题得到规避。

### 11.3 是否需要修改数据库定义

如果使用独立 namespace，现有数据库定义可以保持不变：

- vector size 不变；
- distance metric 不变；
- `qdrant_fact_v2` 不变；
- L/M/H/S collection 结构不变；
- 现有 payload index 可以继续使用。

如果需要在 Qdrant 中直接按 fold、deployment run 或 checkpoint 查询，可以增加以下可选 payload 字段：

```text
deployment_run_id
fold
partition
route_hash
checkpoint_hash
```

Qdrant payload 本身是灵活字段，不一定需要 schema migration；只有高频过滤字段需要建立 payload index。若每个 fold/run 已使用独立 namespace，这些字段主要用于审计，不一定需要索引。

假设路由结果为：

```text

└── segment-C facts

deployment namespace _M
└── 本 sample 无数据
```

## 13. S Assembly 的存储形式

组装 S 时使用同一个 routed extraction run ID，并按 route 从对应 tier 复制：

```text
segment-A → 从 _L 复制
segment-B → 从 _H 复制
segment-C → 从 _L 复制
```

复制到 S 后增加：

```json
{
  "source_collection_tier": "small",
  "source_point_id": "point-id",
  "source_extraction_run_id": "deployment-run-id",
  "assembly_id": "assembly-id",
  "episode_id": "deployment-evaluation-id",
  "policy_version": "checkpoint-or-policy-version"
}
```

QA 检索继续强制使用：

```text
dataset_name
split
sample_id
assembly_id
```

从而隔离其他 sample、fold、run 和 assembly。

## 14. SQLite 账本设计

不建议把 routed-test 数据写入训练路径：

```text
samples/<sample_id>/extraction/candidate_ledger.sqlite3
```

推荐独立目录：

```text
outputs/rl_router/deployment_evaluation/<dataset>/<protocol>/fold_<k>/<method>/<run_id>/
├── manifest.json
├── routes.sqlite3
├── samples.sqlite3
├── aggregate.json
├── extraction/
│   └── <sample_id>/
│       ├── state.sqlite3
│       ├── run.lock
│       ├── deployment_ledger.sqlite3
│       ├── run_ledger.sqlite3
│       └── raw/
└── qa/
    └── evaluations.sqlite3
```

### 14.1 Attempt 账本

`run_ledger.sqlite3 / attempts` 记录：

- initial/schema_repair；
- logical call index；
- transport attempt；
- provider usage；
- input/output Token；
- input/output cost；
- known/estimated/unknown cost；
- latency、HTTP status、request ID 和错误。

### 14.2 Batch 账本

`deployment_ledger.sqlite3 / batches` 记录：

- extraction run ID；
- batch ID；
- sample ID；
- tier；
- segment IDs；
- input/output/total Token；
- input/output/total cost；
- logical call count；
- unknown cost attempts；
- batch status。

### 14.3 Segment 账本

`deployment_ledger.sqlite3 / segment_costs` 记录：

- segment ID；
- route tier；
- allocated Token/cost；
- fact count；
- `ok` 或 `no_fact`；
- truncation 信息。

### 14.4 Failure 账本

`deployment_ledger.sqlite3 / failures` 记录：

- batch 和 segment 范围；
- tier；
- error；
- failed_retryable/failed_terminal；
- failure index 和时间。

## 15. Token 和费用的权威来源

Qdrant fact payload 可以保存分摊到 fact 的 Token 和费用，用于单事实审计，但不能作为总费用的权威来源。

原因包括：

- 一个 batch 可能产生 schema repair；
- 一个 segment 可能没有生成 fact；
- no-fact segment 仍然消耗 Token 和费用，但没有 Qdrant point；
- failed transport attempt 可能有未知费用；
- fact 级费用是分摊值，而不是 provider 原始 usage。

推荐权威顺序：

```text
Attempt ledger
→ API 请求、repair、retry 和 unknown cost 的最细粒度证据

Batch ledger
→ 成功 batch 的 provider Token 和费用汇总

Segment ledger
→ batch Token/费用在 segment 之间的归属

Qdrant fact payload
→ segment 分摊值在 fact 之间的进一步归属
```

论文中的真实提取总成本应从 attempt/batch ledger 汇总，不能简单对 Qdrant fact 的 `allocated_total_cost` 求和。

## 16. Routed Scope Hash 设计

为保证 resume 安全，建议 routed scope hash 使用如下输入：

```json
{
  "dataset": "...",
  "split": "...",
  "fold": 0,
  "partition": "test",
  "split_manifest_sha256": "...",
  "sample_id": "...",
  "segments": [
    ["segment-id", "source-content-hash"]
  ],
  "route": {
    "segment-id": "small"
  },
  "route_hash": "...",
  "checkpoint_sha256": "...",
  "scaler_sha256": "...",
  "prompt_hashes": {},
  "models": {},
  "extraction_config": {},
  "qdrant_namespace": "..."
}
```

只要 checkpoint、route、segment 内容或提取配置发生变化，就必须产生新的 scope hash；原 run ID 不允许继续 resume。

## 17. 超长 Segment 的处理

训练候选阶段需要让同一个 segment 能适配所有被生成的 tier，因此当前准备逻辑可能针对多个 tier 共同检查上下文容量。

routed-test 中，一个 segment 只进入一个实际 tier，所以应按：

```text
segment + assigned tier
```

执行上下文容量检查和必要截断。

不能因为本 sample 使用了 large tier，就让一个实际路由到 small 的 segment 按 large 配置截断；也不能根据所有“被使用 tier”的最严格限制统一截断全部 segment。

截断后仍需：

- 保存原始内容 hash；
- 保存 retained/dropped char count；
- 保存 visible/dropped source IDs；
- 只允许模型引用实际可见 source IDs。

## 18. 实现入口建议

新增脚本：

```text
scripts/evaluate_routed_deployment.py
```

建议参数：

```text
dataset
split
--method
--split-manifest
--fold
--partition test
--checkpoint
--deployment-run-id
--output-dir
--config-dir
--device
--resume
```

脚本执行顺序：

1. 加载配置和 split manifest。
2. 强制 partition 为 outer-test。
3. 校验 test sample IDs。
4. 加载 checkpoint 和 scaler。
5. 校验 checkpoint/fold/manifest 哈希。
6. 加载 sample segments。
7. 构建冻结特征并执行确定性路由。
8. 验证 route 一一覆盖全部 segment。
9. 为每个 segment 按实际 tier 准备上下文。
10. 执行 routed extraction。
11. 写入独立 Qdrant deployment namespace。
12. 组装独立 S assembly。
13. 执行 QA Reader/Judge。
14. 汇总 sample/fold Token、费用和准确率。
15. 完成 manifest 和 reconciliation。

## 19. Reconciliation 建议

当前候选 reconciliation 假设 manifest 的 `required_tiers` 中每个 tier 都完整存在。routed-test 需要独立 reconciliation：

```text
reconcile_routed_extraction_run()
```

校验项包括：

- manifest route 与 route ledger 一致；
- 每个 segment 恰好分配一个 tier；
- state 中每个 committed batch 的 tier 与 route 一致；
- segment ledger 恰好覆盖全部输入 segment；
- Qdrant point 的 tier 与 segment route 一致；
- no-fact segment 在 ledger 中存在，但允许 Qdrant point 数为 0；
- S 中每个有事实的 segment 只来自指定 tier；
- S 中 `source_extraction_run_id` 等于本次 deployment run；
- attempt、batch、segment Token/费用满足守恒关系；
- 未使用 tier 不应出现 batch；
- campaign manifest 和训练 namespace 未发生变化。

## 20. 回归测试要求

### 20.1 训练候选回归测试

- 默认生成仍让每个 segment 进入 small、medium、large。
- `selected_tiers` 的原有语义保持不变。
- campaign 仍要求全部 `required_tiers` 完成。
- `load_replay_history` 仍只接受完整 L/M/H run。
- 当前 candidate reconciliation 继续通过。

### 20.2 Routed Extraction 测试

- 每个 segment 只进入 route 指定 tier。
- A/B 路由到不同 tier 后不会出现在同一 batch。
- 未使用 tier 不产生 batch/API 调用。
- 每个 fact 的 source IDs 只属于其 segment。
- route 缺失、重复或非法 tier 时在 API 调用前失败。
- 同一 run ID 改变 route 后 resume 被拒绝。
- no-fact segment 的 Token/费用仍记录在 segment ledger。
- schema repair 和 retry 进入 attempt/batch 总计。
- Qdrant facts 仅写入 deployment namespace。
- S 只复制本次 routed run 的 facts。

### 20.3 隔离测试

- routed-test 不修改 campaign manifest。
- routed-test 不修改训练候选的 Qdrant point 数。
- routed-test 不写训练 `candidate_ledger.sqlite3`。
- 删除 deployment namespace 不影响训练 namespace。
- 训练脚本无法把 routed run 当作完整 replay history。

## 21. 对现有系统的影响评估

| 范围 | 推荐方案下的影响 |
|---|---|
| 训练候选提取逻辑 | 无行为变化 |
| 强化学习 rollout | 无变化，继续使用冻结候选 |
| Candidate campaign | 无变化，只读引用其 ID/hash |
| Campaign 完整性门禁 | 无变化，继续要求完整 L/M/H |
| Qdrant schema | 不变，新增独立 namespace |
| `qdrant_fact_v2` | 不变 |
| 训练 SQLite ledger | 不变，不写 routed 数据 |
| Routed SQLite ledger | 新增独立目录和文件 |
| S assembly | 复用，但使用 routed extraction run ID |
| QA Reader/Judge | 复用 |
| Token/价格公式 | 复用 |
| 新增风险 | 主要集中在共用 engine 重构和 namespace 配置 |

## 22. 实施顺序

建议按以下顺序开发：

1. 为当前 candidate extraction 增加覆盖关键行为的回归测试。
2. 抽取不包含 tier assignment 策略的通用 ExtractionEngine。
3. 确认 candidate tests 和 campaign reconciliation 全部通过。
4. 实现 `RoutedMemoryExtractor` 和 route scope hash。
5. 实现独立 deployment manifest、ledger 和 Qdrant namespace。
6. 实现 routed reconciliation。
7. 使用小型 fake API/unit test 验证 Token、费用和 S 组装。
8. 使用少量非正式 sample 执行 smoke test。
9. 冻结协议后再运行五折 outer-test 正式实验。

## 23. 最终推荐

增加真实路由记忆提取功能时，不应复制另一套 API、parser、Token 或费用代码，也不应让 routed-test 进入训练 campaign。

最终架构应为：

```text
相同 ExtractionEngine
├── CandidateGenerator：每段生成全部 L/M/H，服务训练
└── RoutedMemoryExtractor：每段只生成路由选中的 tier，服务 outer-test

相同 Fact/Qdrant Schema
├── Training Candidate Namespace
└── Deployment Evaluation Namespace

相同 Run Lock 机制
├── Candidate Scope Hash
└── Routed Scope Hash（额外包含 fold/checkpoint/route）

相同 Token/费用规则
├── 独立 Candidate Ledgers
└── 独立 Deployment Ledgers
```

该方案能够最大限度复用已经经过测试的提取逻辑，同时避免真实测试污染训练候选、campaign、replay history 和数据库 S。
